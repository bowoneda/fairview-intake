# MASTER SPECIFICATION — Project 1: Fairview Compliance Intake Platform

Produced by: Project Architect Skill, Phase 0
Feeds: DESIGN.md, PROCESS-RULES.md

## ONE LINE DESCRIPTION

A white labeled, multi tenant compliance and applicant intake platform that replaces manual paper income verification with connected financial data, a deterministic income determination engine, and automated generation of official regulatory filings, built for a fictional affordable housing and property tax relief program in the State of Meridian.

## FICTIONAL JURISDICTION, HELD CONSTANT

State of Meridian. Ashland County. City of Fairview. The housing authority operating the program is the Fairview Housing Authority, referred to in code and documents as FHA-Meridian to avoid collision with the real Federal Housing Administration abbreviation. The official income certification form generated by the platform is called the Fairview Tenant Income Certification, or FTIC. The county tax relief filing is called the Ashland County Assessor Exemption Filing, or ACAEF. These names are used everywhere: code comments, database table names where relevant, generated PDFs, UI copy, and documentation. No real Illinois, Chicago, or Cook County name appears anywhere in the deliverable.

## MULTI TENANT ARCHITECTURE DECISION

Decision: single Supabase project, single shared schema, tenant isolation enforced entirely through Postgres Row Level Security keyed on a tenant_id column present on every tenant scoped table.

Reasoning: a separate schema or separate database per tenant would be more isolated in theory, but it does not reflect how this kind of platform is actually operated in practice, where a single housing authority vendor serves many client agencies from one deployment and scales by adding rows, not by provisioning new infrastructure per client. The RLS pattern is also the pattern Supabase is built around, and demonstrating it correctly, meaning tenant isolation enforced at the database layer rather than trusted to application code, is one of the more valuable signals this project can carry into a portfolio. Application layer isolation alone is not acceptable on this project. Every query must pass through RLS, and the Security Skill's Phase 1 check exists specifically to try to break that isolation, not just confirm the policy exists.

Every tenant scoped table carries a tenant_id column, a foreign key to a tenants table. RLS policies compare tenant_id against a value read from the authenticated user's JWT claims, set at sign in. Service role keys, which bypass RLS, are used only in narrowly scoped server side Edge Functions that have already authenticated and authorized the request through other means, never exposed to the client.

## WHITE LABEL THEMING

Tenant resolution happens from the URL path, using a slug segment as the first path segment, for example platform.example/fairview/apply, not a subdomain and not a query parameter, since a path segment is cleaner for the applicant facing links this platform generates and shares and needs no per tenant DNS. A theme configuration table, keyed by tenant_id, stores the tenant display name, the jurisdiction names used in generated copy, a logo asset reference, and a small set of brand colors. On request, the Next.js server component resolves the slug, loads the theme row, and injects the brand colors as CSS custom properties at the document root, so no component needs tenant specific styling logic. Only one tenant, FHA-Meridian, is actually configured for this build, but the mechanism must genuinely support adding a second tenant without a code change, since demonstrating that the multi tenant claim is real, not decorative, is part of the point of this build.

## CORE DATA MODEL

Tenant scoping rule for the model below: every table other than tenants itself carries its own tenant_id column, including child tables whose tenant could in principle be derived through a parent. The tenant_id is stored directly so that every RLS policy is a direct comparison against the JWT claim, never a join through a parent table. Child tables reference their parent through a composite foreign key on (parent id, tenant_id), so a child row can never carry a tenant_id different from its parent's.

tenants: id, slug (unique, the URL path segment), display name, jurisdiction names, created at. Readable without authentication, since slug resolution happens before sign in and these columns are public identity only; writable by no client role.

theme_configs: tenant_id, logo reference, brand colors, form footer text. Public branding only, containing nothing sensitive. Readable without authentication, since the theme must render on the applicant landing page before sign in; writable only by that tenant's admin role. This is the only tenant scoped table with an unauthenticated read policy, and that policy is deliberate, not an exception to be tightened later.

users: id (the Supabase Auth user id, which serves as the auth reference), tenant_id (fixed for life), role (applicant, reviewer, admin).

applicants: id, tenant_id, user_id (the applicant's own account, which the applicant level RLS layer keys on, so one applicant cannot read another applicant's household within the same tenant), contact information, current application status. The applicant record is the household's application; the people in the household live in household_members.

household_members: id, tenant_id, applicant_id, full name, relationship to head of household, date of birth, social security number (encrypted at the field level per SECURITY.md, never stored in plaintext). Household size for AMI tier matching is the count of this applicant's household_members rows.

income_sources: id, tenant_id, applicant_id, household_member_id (the member who earns or receives this income), source type (employment, self employment, benefit, other), connection method (Argyle, Plaid, manual upload).

income_records: id, tenant_id, income_source_id, raw ingested data, normalized pay rate, pay frequency, YTD figure, capture date, ingestion method.

asset_records: id, tenant_id, applicant_id, household_member_id (nullable, for assets held jointly by the household), asset type, institution name, full account number (encrypted at the field level per SECURITY.md), account number last four (plaintext, for masked display only), current balance, actual income generated, income determinable flag (true when actual income for this specific asset can be reliably determined from account data, which decides whether imputation applies to it above the threshold, per CALC-SPEC-1.md Part Three).

calculated_determinations: id, tenant_id, applicant_id, calculation version, annualized income figure, imputed asset income figure, total annual income, AMI tier assigned, review required flag, calculation trace (every intermediate value, not just the final number), calculated at, status (draft, pending_review, approved). A determination whose run rate and YTD extrapolation differ by more than the variance threshold is saved as pending_review with no figure auto-selected, per CALC-SPEC-1.md Part Two; the reviewer's selection and written justification are written to audit_log before it can move to approved.

generated_documents: id, tenant_id, applicant_id, determination_id (the exact approved determination the document was produced from), document type (FTIC, ACAEF), generated PDF reference, signature status, generated at.

workflow_state: id, tenant_id, applicant_id, current stage, assigned reviewer, last action, last actor, timestamp. Every transition is appended, never overwritten, forming the audit trail.

audit_log: id, tenant_id, actor, action, target record, timestamp, before and after values where applicable. Append only: no update or delete path exists for any role.

The calculation trace field on calculated_determinations matters more than it looks. Because the Regulatory Compliance Verification Skill's Phase 3 job is to independently re-derive and check the engine's output, the engine must expose every intermediate value it used, not just the final annual income figure. A reviewer or auditor confirming a determination needs to see the annualized run rate, the YTD extrapolation, which one was used and why, the actual asset income, the imputed asset income if the threshold was crossed, and the AMI tier boundary the household landed inside. Storing only the final number would make independent verification impossible and would not reflect how a real compliance system is required to behave.

## MILESTONE PLAN WITH ACCEPTANCE CRITERIA

Milestone 1, architecture and shell. Deliverable: separate development and staging Supabase environments with distinct keys, set up before any schema work; multi tenant Supabase schema live in development with RLS policies on every tenant scoped table; Next.js intake shell resolving tenant from URL slug and rendering FHA-Meridian's theme. Acceptance criteria: the development environment's keys are confirmed distinct from any other environment's; a second, dummy tenant can be inserted and its own theme renders correctly at its own slug without any code change, and an attempt to query one tenant's applicant data while authenticated as a user of a different tenant returns zero rows, verified by an actual query, not by reading the policy definition.

Milestone 2, financial ingestion. Deliverable: Plaid and Argyle sandbox integrations live, Textract fallback pipeline for uploaded documents live. Acceptance criteria: a simulated applicant can complete the Plaid Link sandbox flow and an Argyle Link sandbox flow, and both produce a normalized income_records entry with the same shape regardless of which pipeline produced it. A sample scanned paystub image, run through Textract, also produces an income_records entry in the same shape.

Milestone 3, calculation engine and PDF generation. Deliverable: the deterministic income determination engine built to the calculation specification, and pdf-lib generation of the FTIC and ACAEF forms. Acceptance criteria: full test coverage against every worked example in the calculation specification, independently re-derived and confirmed by the Regulatory Compliance Verification Skill, not just passed by tests the same engineer wrote. Generated PDFs contain the correct values in the correct fields, confirmed by opening the actual generated file, not by trusting the code that wrote it.

Milestone 4, reviewer dashboard and hardening. Deliverable: PII masked reviewer dashboard with manual exception resolution, full security audit pass. Acceptance criteria: SSNs and full account numbers are masked in the dashboard UI and confirmed masked in what actually renders, not only in the database schema. Security Skill's full STRIDE pass produces no unresolved high severity finding.

Milestone 5, deployment. Deliverable: staged deployment on Vercel and Supabase, separate from local development credentials, with the Deployment Skill's checklist run and passed. Acceptance criteria: RLS is confirmed active against the deployed database specifically, not assumed to carry over from local development, by running the same cross tenant query attempt against the live environment.

## OPEN DECISIONS CARRIED FORWARD

Resolved into CALC-SPEC-1.md: the exact AMI tier schedule for Fairview is fictional and is defined in the calculation specification, since real HUD AMI tables are tied to a real published fiscal year and a real geographic area and using one would contradict the genericization rule. The variance threshold used to decide when annualized run rate and YTD extrapolation disagree enough to require manual review is also defined in the calculation specification, since that is a compliance judgment call, not an architecture decision.

Still open, each to be resolved before the phase that depends on it:

Income above the highest tier (Phase 3). CALC-SPEC-1.md's tier rule assigns the lowest tier whose threshold is at or above the household's income, but does not say what happens when income exceeds the eighty percent tier. The engine must not guess. Resolve through the Regulatory Compliance Verification Skill and add to CALC-SPEC-1.md, with a worked example, before the engine is built.

Effective year of the asset threshold and passbook rate (Phase 3). The real fifty thousand dollar HOTMA threshold is adjusted annually for inflation, and the passbook rate is republished periodically. The configuration module named in RULES.md must record which year's values it uses as a documented project convention, confirmed by the Regulatory Compliance Verification Skill, rather than presenting fifty thousand dollars and zero point four percent as permanent constants.

E-signature provider (Phase 3). DocuSign or Dropbox Sign. Choose before Phase 3 begins and log the decision and reason in MEMORY.md.
